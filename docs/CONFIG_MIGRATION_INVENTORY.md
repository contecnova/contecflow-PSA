# Settings Inventory — Migration Plan to UI-Backed Configuration

Generated by reviewing [app/core/config.py](../app/core/config.py) and
[app/core/config_groups/](../app/core/config_groups/) (~170 settings total).

Each setting is tagged with one of four targets:

| Tag | Storage | Editable from | Reason |
|---|---|---|---|
| 🔴 **bootstrap** | env var only | redeploy | Needed before DB or process can start; or affects startup ordering and a UI change still requires restart |
| 🟠 **org_secret** | `app_settings` table, **encrypted** (`app/services/key_management.py`) | Settings UI, org-admin | Per-tenant credentials & operational secrets — already partly DB-based (e.g. `JiraConfig`) |
| 🟢 **runtime_flag** | `app_settings` table | Settings UI, super-admin | Operational knob with no startup ordering constraint; can be cached + reloaded |
| ⚪ **keep_env** | env var | redeploy | Could be moved but pragmatically not worth the churn (defaults for constants, API base URLs that almost never change, internal dev defaults) |

The destination table `app_settings` already exists at
[app/models/settings.py:7](../app/models/settings.py#L7) (key-value, with
`organization_id IS NULL` for global rows and non-NULL for tenant overrides).

## Summary by tag

| Tag | Count (approx) | Action |
|---|---|---|
| 🔴 bootstrap | ~30 | Keep in env. Document required vs optional in [.env.example](../.env.example) |
| 🟠 org_secret | ~30 | New `IntegrationConfig` tables (or extend `app_settings` with encryption) — UI per integration |
| 🟢 runtime_flag | ~85 | Move to `app_settings` with admin UI sections per category |
| ⚪ keep_env | ~25 | Leave in env; not worth migrating |

## Recommended migration order

1. **Phase 1 — business policy knobs (🟢, biggest win, lowest risk).**
   SLA hours, health weights/thresholds, semantic thresholds, password policy,
   locale/currency/tax, timeout overrides. ~85 settings; no startup-order
   coupling, no secrets, no UI auth surface to design (just admin-only forms).
   Add a thin `settings_service.get_int/bool/float(key, default)` that reads
   from `app_settings` (with org_id resolution) and falls back to env, plus an
   in-process cache invalidated on PUT.

2. **Phase 2 — integration credentials (🟠).**
   SMTP, AWS S3 keys, Azure/Graph, Slack, Twilio, Stripe, DocuSign, Adobe Sign,
   AI provider keys. Reuse `key_management.encrypt_secret()` for storage.
   Build one reusable React form component "IntegrationCard" with test-connection
   button per provider. Existing `JiraConfig` is the reference implementation.

3. **Phase 3 — keep the rest in env (🔴 + ⚪).**
   Document them in [.env.example](../.env.example) with `# bootstrap` markers
   so it's clear they cannot move.

## Out of scope (intentionally not moved)

- **Bootstrap secrets** (`SECRET_KEY`, `DATABASE_URL`, `SUPERADMIN_*`): UI
  exposure adds attack surface with no operational gain — these change once
  per deploy.
- **Module-load-time settings** (Sentry DSN, OTEL endpoint, METRICS_ENABLED,
  KMS provider): moving them to DB and not restarting would silently fail to
  apply. Better to keep the "change → redeploy" contract.
- **Routing/CORS/cron timings**: bound to FastAPI/APScheduler at startup.
