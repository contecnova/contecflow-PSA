# Alembic Migration Naming Convention

This document captures the migration-naming conventions observed in `alembic/versions/`
and the standard to follow for **future** migrations.

> NOTE: existing migrations are intentionally **not** renamed. Renaming a revision
> changes its identifier, which would force every environment to manually re-stamp
> Alembic, with high risk of state divergence. We freeze history and standardize
> moving forward.

These use a short numeric prefix as `revision` (e.g. `revision = "060_workflow_runtime"`).
They were authored manually during early stages and remained sequential while a
single developer owned the chain.

### 2. UUID-prefix (autogenerated, Alembic default)

Files like:

```
115e52e0a1b2_add_soft_delete_is_active_to_okrs_.py
1b6d9fd29b10_enterprise_soft_delete_alignment.py

...
```

These were produced by `alembic revision --autogenerate -m "..."` and use the
default 12-char hex revision id. They became common once multiple branches/PRs
needed to add migrations in parallel (numeric prefixes collide across branches).

## Standard for new migrations

**Use `NNN_nombre_en_castellano`**: the next free three-digit number and a short
descriptive name in Spanish (the language of the code and its docstrings). The
file name and the revision id are the same string. Since `086` this is how every
migration is named, for example:

```
195_flujo_de_demanda.py            revision = "195_flujo_de_demanda"
196_auditoria_2026_11_22.py        revision = "196_auditoria_2026_11_22"
197_dinero_numeric.py              revision = "197_dinero_numeric"
198_cambios_estandar_y_portal.py   revision = "198_cambios_estandar_y_portal"
```

Write the file by hand (there is no need to run `alembic revision`; if you do,
rename the file and the `revision` to this format before anything else):

```bash
python -m alembic heads        # exactly one head: its number + 1 is yours
```

### Rules

1. **Revision id**: `NNN_nombre`, equal to the file name without `.py`. `NNN` is
   the head's number plus one (a gap is harmless, but do not reuse a number).
   `alembic_version.version_num` is widened to `VARCHAR(255)` by `alembic/env.py`,
   so the 32-character default does not limit the name.
2. **Name** (the part after `NNN_`):
   - lowercase, `snake_case`, in Spanish, ASCII only (no accents or `ñ`)
   - says what the migration does, not how: `flujo_de_demanda`,
     `dinero_numeric`, `cambios_estandar_y_portal`
   - Bad: `update_tables`, `migracion1`, `fix-stuff` (vague, English, kebab-case)
3. **`down_revision`**: the exact revision id of the current head (a string like
   `"197_dinero_numeric"`). Run `python -m alembic heads` before authoring to
   confirm there is exactly one head; `scripts/migrar.py` refuses to run with two.
   If two agents or branches add a number at the same time, one of them re-points
   its `down_revision` to the other (do not leave two heads).
4. **Idempotency for cross-engine support**: this project supports both SQLite
   (dev) and PostgreSQL (prod). New migrations must guard schema introspection,
   e.g.:

   ```python
   bind = op.get_bind()
   insp = sa.inspect(bind)
   if "my_table" not in insp.get_table_names():
       op.create_table(...)
   ```

5. **Docstring header**: a first line that says what it does, a paragraph with the
   intent, the tables and columns touched, what happens to existing data and what
   `downgrade` does, then `Revision ID:` and `Revises:`. `docs/DESPLIEGUE.md`
   (B.2) is written from these docstrings, and a new migration adds its row there.
6. **Indexes**: prefer creating indexes inside the same migration that creates
   the column. For composite indexes follow the equality-before-range rule.
7. **Tables with `organization_id`**: no policy is written by hand; `alembic/env.py`
   applies row-level security after every `upgrade` (`app/db/rls.py`).

### File-name format

```
198_cambios_estandar_y_portal.py
^^^ ^^^^^^^^^^^^^^^^^^^^^^^^^^^^
num name in Spanish
```

The older hex files (`3f7a9c2d1e55_tasks_dependencies_soft_delete_alignment.py`)
keep their names: history is frozen.

## Destructive revisions (audit 2026-11-22, 01 M10)

runs `DELETE`/`TRUNCATE` (same rule as `scripts/copia_antes_de_migrar.py`, which

## Quick checklist (copy into PR description)

- [ ] Named `NNN_nombre_en_castellano` (next free number; file name = revision id)
- [ ] `down_revision` points to current head (`python -m alembic heads`, a single head)
- [ ] Row added to `docs/DESPLIEGUE.md` (B.2)
- [ ] Migration is idempotent against both SQLite and PostgreSQL (guarded with `inspect`)
- [ ] `downgrade()` implemented (or explicitly marked `pass` with comment if irreversible)
- [ ] New composite indexes follow equality-before-range column order
- [ ] No PII / production secrets in the migration body
- [ ] If `upgrade()` drops or deletes, listed under «Destructive revisions» above
