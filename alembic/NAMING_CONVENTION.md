# Alembic Migration Naming Convention

This document captures the migration-naming conventions observed in `alembic/versions/`
and the standard to follow for **future** migrations.

> NOTE: existing migrations are intentionally **not** renamed. Renaming a revision
> changes its identifier, which would force every environment to manually re-stamp
> Alembic, with high risk of state divergence. We freeze history and standardize
> moving forward.

---

## Current state (audit, May 2026)

Two styles coexist in `alembic/versions/`:

### 1. Numeric-prefix sequential (legacy, hand-written)

Files like:

```
001_initial_tables_initial_tables.py
060_workflow_runtime.py
070_perf_questions_team.py
071_perf_360_campaigns.py
072_dev_plans.py
073_fk_indexes.py
074_org_require_mfa.py
075_user_organization_memberships.py
076_multitenancy_org_id_columns.py
077_soft_delete_and_constraints.py
078_normalize_task_status_review.py
079_more_soft_delete.py
```

These use a short numeric prefix as `revision` (e.g. `revision = "060_workflow_runtime"`).
They were authored manually during early stages and remained sequential while a
single developer owned the chain.

### 2. UUID-prefix (autogenerated, Alembic default)

Files like:

```
115e52e0a1b2_add_soft_delete_is_active_to_okrs_.py
1b6d9fd29b10_enterprise_soft_delete_alignment.py
2c7d1e9a4f10_capacity_soft_delete_alignment.py
2f165b37fe82_fix_soft_delete_uniqueness_partial_.py
3f7a9c2d1e55_tasks_dependencies_soft_delete_alignment.py
4a1c9e8d7b33_changes_soft_delete_alignment.py
...
```

These were produced by `alembic revision --autogenerate -m "..."` and use the
default 12-char hex revision id. They became common once multiple branches/PRs
needed to add migrations in parallel (numeric prefixes collide across branches).

## Standard for new migrations

**Use Alembic's default hex-prefix style.** Concretely:

```bash
alembic revision --autogenerate -m "short_imperative_description"
# or for manual migrations:
alembic revision -m "short_imperative_description"
```

### Rules

1. **Revision id**: keep the autogenerated 12-char hex prefix. Do **not** override
   with a numeric prefix — numeric prefixes collide across branches and force
   painful rebases.
2. **Message slug** (the part after the `_` in the filename and the `-m` argument):
   - lowercase, `snake_case`
   - imperative or descriptive noun phrase
   - ≤ 60 chars
   - Good: `add_soft_delete_to_okrs`, `enterprise_soft_delete_alignment`,
     `fk_indexes_on_audit_tables`
   - Bad: `Update Tables`, `migration1`, `fix-stuff` (no kebab-case, no vague names)
3. **`down_revision`**: must point to the current head. Run `alembic heads`
   before authoring to confirm there is exactly one head. If there are two heads,
   author a merge revision (`alembic merge -m "merge_heads"`).
4. **Idempotency for cross-engine support**: this project supports both SQLite
   (dev) and PostgreSQL (prod). New migrations must guard schema introspection,
   e.g.:

   ```python
   bind = op.get_bind()
   insp = sa.inspect(bind)
   if "my_table" not in insp.get_table_names():
       op.create_table(...)
   ```

5. **Docstring header**: keep the docstring Alembic generates (revision id,
   revises, create date). Add a short paragraph explaining the *intent* of the
   change when non-obvious.
6. **Indexes**: prefer creating indexes inside the same migration that creates
   the column. For composite indexes follow the equality-before-range rule
   (see `docs/INDEX_TUNING.md`).

### File-name format

Alembic produces `<revision_id>_<slug>.py` automatically. Do not rename the file.

```
3f7a9c2d1e55_tasks_dependencies_soft_delete_alignment.py
^^^^^^^^^^^^ ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
hex prefix   message slug
```

## Quick checklist (copy into PR description)

- [ ] Generated via `alembic revision [--autogenerate] -m "snake_case_description"`
- [ ] `down_revision` points to current head (`alembic heads`)
- [ ] Migration is idempotent against both SQLite and PostgreSQL (guarded with `inspect`)
- [ ] `downgrade()` implemented (or explicitly marked `pass` with comment if irreversible)
- [ ] New composite indexes follow equality-before-range column order
- [ ] No PII / production secrets in the migration body
